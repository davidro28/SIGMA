Use Case Note
■ Workflow
    • El Gestor de tickets, administrador crea una solicitud; adicional, asignan a un técnico y la supervisa hasta su resolución.
■ Business Logic
    • Las solicitudes deben contener información mínima obligatoria (activo, descripción, prioridad).
    • Solo roles autorizados pueden modificar, cancelar o cerrar solicitudes.
    • Cada solicitud debe estar asociada a un activo existente
■ Decisions
    • Definir si la cancelación requiere justificación.
    • Determinar si el cierre solo puede realizarlo el técnico o también el administrador
■ Follow-up
    • Generación de reportes de solicitudes atendidas.

Scenario
Steps
1. Administrador
2. Tecnico de Mantenimiento
3. El usuario ingresa al sistema y selecciona la opción Gestionar Solicitudes de Mantenimiento.
4. El sistema muestra la lista de solicitudes registradas.
5. El usuario (según permisos) elige una acción: crear, modificar, asignar, cancelar o cerrar una solicitud.
6. El sistema valida los permisos y estado de la solicitud.
7. El sistema ejecuta la acción seleccionada:
8. (a)Si se crea, se registra la nueva solicitud.
9. (b)Si se modifica, se actualiza la información.
10. (c)Si se asigna, se vincula un técnico.
11. (d)Si se cancela, se actualiza el estado a Cancelada.
12. (e)Si se cierra, se marca como Resuelta.
13. El sistema muestra confirmación de la acción.

Scenario2
Steps
1. 6(a). El usuario intenta una acción sin permisos → el sistema deniega la operación.
2. 7(a). Se intenta asignar técnico inexistente o inactivo → el sistema rechaza la acción.
3. 7(b). El activo asociado no existe o fue dado de baja → el sistema bloquea la solicitud.
