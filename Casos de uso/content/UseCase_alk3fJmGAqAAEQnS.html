Gestion de Tickets : System

Use Case - Modificar Ticket link

Properties
Name Value
Description

describe el proceso mediante el cual un actor autorizado modifica un ticket previamente creado en el sistema de gestión de activos.
El actor puede actualizar campos como: descripción del problema, prioridad, estado del ticket, asignación de responsable, o adjuntar información adicional.
Una vez modificado, el sistema registra los cambios con la fecha, hora y usuario que realizó la modificación, y notifica a las partes interesadas.

Use Case Note
■ Workflow
    • El actor autorizado accede al módulo de tickets en el sistema de gestión de activos.
    • Selecciona el ticket que desea modificar desde la lista de tickets abiertos o en progreso.
    • Realiza los cambios necesarios (estado, prioridad, responsable, descripción, adjuntos).
    • Guarda los cambios y el sistema actualiza el registro.
■ Business Logic
    • El sistema debe validar que el usuario tenga permisos para modificar el ticket.
    • El sistema debe mantener un historial de modificaciones (qué campo se cambió, fecha, usuario que lo modificó).
    • El sistema debe notificar automáticamente a los actores relacionados con el ticket (responsable asignado, solicitante).
■ Decisions
    • Solo ciertos roles (Administrador, Gestor de Tickets, Responsable) pueden modificar información crítica (estado, prioridad, asignación).
    • Los usuarios finales solo podrán agregar comentarios o adjuntos, pero no cambiar estado o responsable.
    • Se decidió que el sistema debe registrar todas las modificaciones en un log de auditoría.
■ Follow-up
    • Definir si las notificaciones deben enviarse por correo electrónico, notificación interna o ambos.
    • Asegurar la integración del historial de modificaciones con reportes de auditoría.
    • Revisar con el equipo de soporte si se requieren permisos diferenciados para cada tipo de modificación.

Scenario
Steps
1. Gestor de Tickets
2. Administrador
3. El actor autorizado accede al sistema de gestión de activos.
4. El actor navega al módulo de Gestión de Tickets.
5. El actor selecciona el ticket que desea modificar desde la lista.
6. El sistema muestra los detalles del ticket.
7. El actor edita los campos permitidos (estado, prioridad, responsable, descripción, adjuntos).
8. El actor confirma y guarda los cambios.
9. El sistema valida los permisos del actor.
10. El sistema actualiza la información del ticket.
11. El sistema registra en el historial las modificaciones (fecha, usuario, campo cambiado).
12. El sistema notifica a los actores involucrados sobre los cambios realizados.

Scenario2
Steps
1. Usuario sin permisos suficientes:
2. En el paso 9, si el sistema detecta que el actor no tiene permisos para modificar ciertos campos, muestra un mensaje de error y cancela la operación.

Scenario3
Steps
1. Ticket inexistente o cerrado:
2. En el paso 5, si el ticket ya no existe o está en estado Cerrado, el sistema informa que no puede modificarse.

Scenario4
Steps
1. Error en el sistema:
2. Si ocurre un fallo técnico durante el guardado (paso 8 o 10), el sistema muestra un mensaje de error y no se aplican los cambios.

Implementation Status
Preconditions El usuario debe estar autenticado en el sistema. Debe existir al menos un ticket previamente registrado. El usuario debe contar con permisos de modificación (Administrador, Gestor de Tickets o Responsable). Modificar Activo
Post-conditions El ticket queda actualizado con la nueva información registrada. Se genera un registro en el historial con los detalles de la modificación (quién, qué, cuándo). Los actores relacionados reciben notificación de los cambios.
Author
Assumptions Se asume que el sistema se encuentra disponible durante la operación. Se asume que los cambios realizados son consistentes con la política de soporte (no se modifican tickets ya cerrados sin autorización especial). Se asume que la conectividad de red es estable para permitir guardar los cambios correctamente.
