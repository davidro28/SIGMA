Description

Use Case Note
■ Workflow
    • El actor autorizado busca la solicitud, actualiza la información requerida y confirma la modificación.
■ Business Logic
    • Solo las solicitudes en estado Pendiente o En proceso pueden modificarse.
    • Ciertos campos (ej. activo asociado) no pueden cambiarse después de la creación.
    • Debe mantenerse un historial de modificaciones.
■ Decisions
    • Determinar qué roles pueden editar campos sensibles (ej. prioridad, técnico asignado).
    • Decidir si siempre se requiere justificación para cambios.
■ Follow-up
    • Notificación automática a los actores afectados.

Scenario
Steps
1. Administrador
2. Tecnico de Mantenimiento
3. El actor autorizado accede al sistema e ingresa al módulo Modificar Solicitud.
4. El sistema solicita identificar la solicitud (ID, código o búsqueda).
5. El sistema muestra la información actual de la solicitud.
6. El actor edita los campos disponibles (ej. descripción, prioridad, comentarios).
7. El sistema valida permisos y consistencia de los datos.
8. El actor confirma la modificación.
9. El sistema guarda los cambios en la base de datos.
10. El sistema notifica a los actores relacionados (técnico, administrador).
11. El sistema muestra mensaje de confirmación.

Scenario2
Steps
1. 4(a). El actor ingresa un ID de solicitud inexistente → el sistema informa que no se encontró.
2. 5(a). La solicitud está en estado Cerrada o Cancelada → el sistema no permite modificaciones.
3. 7(a). El actor intenta modificar un campo restringido → el sistema bloquea la acción.
4. 9(a). Falla en la base de datos → el sistema cancela la operación e informa el error.
